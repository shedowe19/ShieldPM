# Internationalisierung (i18n)

## Zweck

Dokumentation des Übersetzungssystems und aller unterstützten Sprachen.

## Kontext

ShieldPM verwendet `i18next` + `react-i18next` für die Internationalisierung. Übersetzungsdateien liegen unter `frontend/src/locale/`.

## Wichtige Dateien

| Datei                           | Zweck                                           |
| ------------------------------- | ----------------------------------------------- |
| `locale/index.ts`               | Einstiegspunkt                                  |
| `locale/IntlProvider.tsx`       | i18n-Provider-Komponente (3.5 KB)               |
| `locale/Utils.ts`               | Locale-Hilfsfunktionen                          |
| `locale/Utils.test.tsx`         | Tests für Locale-Utilities                      |
| `locale/README.md`              | Anleitung zum Hinzufügen neuer Sprachen         |
| `locale/scripts/locale-sort.sh` | Script zum Sortieren von Übersetzungsschlüsseln |

## HelpDoc-System

Unter `locale/HelpDoc/` befinden sich Markdown-Hilfetexte pro Sprache und Feature:

| Sprache          | Themen                                                                                                                           |
| ---------------- | -------------------------------------------------------------------------------------------------------------------------------- |
| pro Sprache (13) | AccessLists, Certificates, CloudflaredTunnels, DdnsProviders, DeadHosts, ProxyHosts, RedirectionHosts, Streams, TorOnionServices |

Jede Sprache hat 9 Hilfe-Dateien + 1 `index.ts`. Die Hilfe wird im Frontend über `HelpModal.tsx` angezeigt.

## Neue Sprache hinzufügen

1. Erstelle `frontend/src/locale/lang/XX.json` (kopiere `en.json`)
2. Aktualisiere `frontend/src/locale/IntlProvider.tsx` (`localeOptions` und Imports)
3. Erstelle `frontend/src/locale/HelpDoc/XX/` mit allen Hilfe-Dateien
4. Ergänze `lang-list.json` mit dem nativen Sprachnamen

## Locale-Prüfung

`frontend/check-locales.cjs` nutzt `en.json` als Source of Truth für alle Keys. Jede unterstützte Sprache muss alle Keys aus `en.json` enthalten; fehlende Keys sind Fehler und dürfen nicht mehr nur als Warnung durchlaufen.

Zusätzlich prüft der Checker englische Fallbacks: Wenn ein nicht-englischer Wert exakt mit `en.json` übereinstimmt, ist das nur für eine technische Allowlist erlaubt (z.B. Protokolle, Produktnamen, IDs, Platzhalter, Code-Beispiele oder bewusst unveränderte technische Labels). Alle anderen identischen Werte gelten als wahrscheinlicher englischer Fallback und brechen den Check.

Der Checker ruft `formatjs` über `yarn exec formatjs extract "src/**/*.tsx"` auf. Wichtig: Das Glob-Argument darf im `spawnSync`-Array nicht zusätzlich mit Shell-Quotes (`'src/**/*.tsx'`) übergeben werden, sonst findet FormatJS keine Dateien. Der Exit-Code der Extraktion wird geprüft, damit eine leere Temp-JSON nicht fälschlich als erfolgreicher Locale-Check zählt. Generische Laufzeit-Übersetzer wie `src/locale/IntlProvider.tsx` und dynamische Notification-Helper werden bei der Extraktion ignoriert, weil sie bewusst variable IDs entgegennehmen und keine statisch extrahierbaren Message-Definitionen sind.

Sprachnamen in `lang-list.json` sollen nativ sein (z.B. `Deutsch`, `Nederlands`, `Español`) und nicht englische Bezeichnungen enthalten.

User-facing UI-Text darf nicht hardcoded in TSX stehen. Sichtbare Labels, Beschreibungen, Alert-Titel und Buttontexte müssen über `<T id="..." />` oder `intl.formatMessage({ id: "..." })` aus den Locale-Dateien kommen. Hardcodete TSX-Texte umgehen die Locale-Dateien und werden von Key-Vollständigkeitsprüfungen nicht automatisch übersetzt.

## Abhängigkeiten

- `i18next` — Kern-i18n-Framework
- `react-i18next` — React-Bindings
- `i18next-browser-languagedetector` — Auto-Erkennung der Browser-Sprache
